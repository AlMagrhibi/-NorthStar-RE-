# Original launcher workflow (generic)
Use `client-compatibility-analysis`, `dependency-mapping`, `advanced-binary-intelligence`, `ghidra-native-analysis`, `dynamic-runtime-analysis`, and `client-server-interoperability` as appropriate. First identify launch chain and configuration dependencies from static evidence; a PDB path is an identity clue, not source code. Verify actual signature trust separately. No unpacking is needed when no packing evidence exists. A string reference does not prove runtime use. Separate supported config schemas from protected/unknown config; do not derive or extract protected keys, defeat signature validation, or impersonate third-party authentication. Approved key-based recovery only. For isolated runtime use disposable guest, network disconnected, no writable host mappings or credentials; request separate approval for elevation, feature enablement or reboot. Collect module/process/file access diagnostics without protected memory dumps or secrets. Prefer documented interfaces and a synthetic local fixture; original launcher remains unmodified and no replacement launcher is a final deliverable. Keep existing servers working and distinguish internal test client from actual compatibility. Record verified/partial/blocked results in Markdown and JSON.
